Calibrate the camera crop

Do this first, before recording anything — every downstream step (dataset images, the classifier, the policy) depends on _processor()'s hardcoded crop_params_dict={"left": [...]} actually framing the workpiece. Re-run it any time the camera moves.

MPLBACKEND=qtagg python src/share/scripts/utils/find_crop_params.py \
  --env.type=rail_bimanual_grasp

Env-agnostic — it connects whatever cameras rail_bimanual_grasp configures (just "left" here), not a hoermann-specific tool. Drag a box around the workpiece in the window that opens, press w to print [top, left, height, width], q to quit. No --object_dir given, so nothing gets written automatically — copy the printed box into crop_params_dict in rail_bimanual_grasp.py's _processor() by hand.

Setup

Run every command below from the repo root. Only cooperative_insert — the one primitive with a policy attached — ever gets recorded; every other primitive (align, grasp, calibrate, reset) is scripted or manual setup and produces no dataset frames.

# repo root: /home/jstranghoener/PyCharmProjects/share-rl
export DATASET_ROOT=/media/internal/nvme/shared_data/weidmueller/insertion/data
export DATASET_REPO_ID=insertion
export JOB_NAME=rail_bimanual_grasp_sac
A

Record demonstrations

skip_grasp=false walks the full setup chain once — align to the rail, grasp left, grasp right, zero the F/T sensors, teleop ry to the right angle — then loops cooperative_reset ⇄ cooperative_insert. Only the cooperative_insert half of that loop is recorded; the setup chain never repeats after the first pass.

python src/share/scripts/record.py \
  --env.type=rail_bimanual_grasp \
  --env.skip_grasp=false \
  --env.mock=false \
  --use_policy=false \
  --dataset.root=$DATASET_ROOT \
  --dataset.repo_id=$DATASET_REPO_ID \
  --dataset.num_episodes=30 \
  --dataset.single_task="Insert the workpiece" \
  --dataset.push_to_hub=false
SUCCESS fires on either SpaceMouse button or space; STOP_RECORDING is the other SpaceMouse button or the down arrow. Demonstrate genuine variety in cooperative_insert — successes and realistic near-misses — the classifier in step B learns entirely from this data.

Writes to $DATASET_ROOT/cooperative_insert as repo id $DATASET_REPO_ID-cooperative_insert. Each episode auto-truncates after 5s if nothing else has fired yet (cooperative_insert_episode_duration_s, overridable with --env.cooperative_insert_episode_duration_s=<seconds>).

Find the checkpoint

Step C needs an actual checkpoint path — the step-numbered folder varies per run:

find $DATASET_ROOT/reward_classifier/checkpoints -maxdepth 1 -type d | sort
# pick the highest step, then point at its pretrained_model subfolder:
export CLASSIFIER=$DATASET_ROOT/reward_classifier/checkpoints/002000/pretrained_model
C

Bootstrap more demonstrations

Same recording run, now with the classifier live and skip_grasp=true — jump straight into zero_ft_before_cooperative → cooperative_reset instead of re-grasping and re-calibrating ry every session. This assumes the rig is still physically holding the rail from step A — ry gets re-measured from the arm's actual pose, not a stored value, so as long as it hasn't moved, it comes out right on its own.

python src/share/scripts/record.py \
  --env.type=rail_bimanual_grasp \
  --env.skip_grasp=true \
  --env.mock=false \
  --env.reward_classifier_path=$CLASSIFIER \
  --env.reward_classifier_threshold=0.7 \
  --env.reward_classifier_device=cuda \
  --use_policy=false \
  --resume=true \
  --dataset.root=$DATASET_ROOT \
  --dataset.repo_id=$DATASET_REPO_ID \
  --dataset.num_episodes=60 \
  --dataset.single_task="Insert the workpiece" \
  --dataset.push_to_hub=false

The classifier is an additional automatic SUCCESS trigger, not a replacement — manual (space/button) and the 5s time limit still work exactly as before, whichever fires first wins. --dataset.num_episodes is the running total the dataset should reach, not an added count — 60 here assumes step A already left it at 30.

D

Actor / learner RL

The learner claims the robots' RTDE registers first, reads feature shapes, then releases them — start it first and wait for it to log ROBOT_RELEASED before starting the actor, or the actor's connection collides with the learner's. Neither command passes --policy.path: leaving it unset keeps cooperative_insert's own baked-in fresh SACConfig(device="cpu", storage_device="cpu").

Learner — start first, wait for ROBOT_RELEASED

python src/share/scripts/learner_server.py \
  --env.type=rail_bimanual_grasp \
  --env.mock=false \
  --env.skip_grasp=true \
  --env.reward_classifier_path=$CLASSIFIER \
  --env.reward_classifier_threshold=0.7 \
  --dataset.root=$DATASET_ROOT \
  --dataset.repo_id=$DATASET_REPO_ID \
  --job_name=$JOB_NAME \
  --wandb.enable=true \
  --wandb.project=rail_bimanual_grasp

Actor — foreground, after ROBOT_RELEASED

python src/share/scripts/actor_server.py \
  --env.type=rail_bimanual_grasp \
  --env.mock=false \
  --env.skip_grasp=true \
  --env.reward_classifier_path=$CLASSIFIER \
  --env.reward_classifier_threshold=0.7 \
  --dataset.root=$DATASET_ROOT \

Reconnecting a dropped actor: rerun its command unchanged — same --job_name, same dataset flags. The learner keeps running with its checkpoints in place; stop it deliberately (Ctrl-C in its own pane) only when you mean to.

If you get stuck in a singularity

Recovery

Force mode itself is what's stuck — turn it off to drive clear

A force-mode singularity can leave the arms stuck under cooperative_reset's normal compliant teleop, with no way to move away from it — the compliant controller is what's caught, so no amount of pushing through it with the SpaceMouse helps. The only way out is rigid, non-compliant teleop: --env.cooperative_reset_servo_recovery=true makes cooperative_reset itself servo-position-controlled instead of force-controlled (the same use_force_mode=false + simple_pose_use_servo=true combination align_to_rail/zero_ft already use), so the SpaceMouse streams rigid position commands you can drive out of the singularity with. It requires skip_grasp=true — enforced, raises a ValueError otherwise — since it only makes sense entering straight into the stuck loop.

python src/share/scripts/record.py \
  --env.type=rail_bimanual_grasp \
  --env.mock=false \
  --env.skip_grasp=true \
  --env.cooperative_reset_servo_recovery=true \
  --use_policy=false \
  --dataset=null

Drive the arms clear with the SpaceMouse, stop the process, then start your normal command again with cooperative_reset_servo_recovery left out (or explicitly false) — it's a recovery switch, not a normal operating mode, and cooperative_insert's own compliance is untouched by it either way.

Notes from reading the config

Added this session

Up arrow in cooperative_reset re-teleops ry, no full reset needed

Jumps straight to calibrate_ry_angle (unlocks ry for live teleop again) without walking back through align_to_rail/teleop_left/teleop_right. calibrate_ry_angle's own success edge already routes back through zero_ft_before_cooperative → cooperative_reset afterward, so it's a self-contained detour, not a new loop shape. Bound nowhere else.

Added this session

cooperative_insert's observation grew delta-position and previous-action

On top of the driver-only xyz velocity every other cooperative primitive gets, cooperative_insert now also observes delta position from wherever the driver was when the episode started, and the previous step's action — closer to Markovian without needing pose history. Both reuse existing observation-state slots with custom axis names (dx/dy/dz.ee_pos, prev_x/prev_y/prev_z.ee_vel) rather than a new shared processor step. dataset_stats["observation.state"] is set explicitly to match — position bound is half of cooperative_insert_position_range_m (default 0.05, i.e. an assumed 5×5×5 cm cube), previous-action shares translation_action_scale since it's that same m/s quantity, one step delayed.

Added this session

5-second auto-truncation on cooperative_insert

The graph had no timeout at all before — an episode ran until SUCCESS or the classifier fired, full stop. Added cooperative_insert_episode_duration_s: float = 5.0 plus an OnTimeLimit(source="cooperative_insert", target="cooperative_reset", …) edge, mirroring the pattern used elsewhere for insertion tasks. It's listed first among cooperative_insert's outgoing edges as a safety fallback, but in practice never races the manual/classifier triggers — it only fires when neither has. Tests updated and passing (35/35).

Added this session

Reproducible ry via --env.ry_angle

calibrate_ry_angle's live teleop-and-measure now has a reproducible alternative: ry_angle supplies an exact value instead of freezing whatever the arm's actual pose happens to measure on entry — no run-to-run variance from a fresh grasp or re-home. Requires skip_grasp=true (enforced, raises a ValueError otherwise) — calibrate_ry_angle is unreachable there anyway, and ry_angle is what fills in for it. Fixed a real bug along the way: naively wiring the override in made CooperativeFramePrimitive capture the driver's grasp-geometry offset from its raw measured pose, which silently reconstructed the original (un-overridden) value the moment a target got sent — the override looked like it took effect internally but never reached the robot.

Added this session

Driver-only, xyz-only velocity observation — dropped the redundant/rotated signal

Traced through share/processor/observation.py: each robot's .ee_vel was read straight from its own raw observation, uncomposited through robot_base_pose_in_world or the vtcp rotation — left and right reported velocity in two different native/base frames, six axes each, most of it either redundant (both arms move together, up to inertia) or meaningless (rotation is locked entirely in every cooperative primitive). Every primitive sharing cooperative_processor — zero_ft through cooperative_insert — now observes just the driver's xyz velocity (3 values, down from up to 12): a clean, near-Markovian signal instead of two robots' worth of largely-redundant, differently-rotated noise. align_to_rail/teleop_left/teleop_right keep the old broad default — they don't feed a policy.

Resume support

pivot_offset_x isn't carried across process restarts

Unlike ry (re-measured from the arm's actual pose every activation, so it survives a restart on its own), pivot_offset_x lives only in shared runtime state, cleared on every full reset. If step A's live ,/. tuning found a good value, pass it explicitly in steps C and D — --env.pivot_offset_x=<value> — or it silently restarts from 0.0 and re-tunes live in cooperative_reset.

alignment_linear_speed_mps is now 0.05, not 0.01

Changed on disk from 1 cm/s to 5 cm/s while this doc was being written — confirmed intentional. Updated the one test that still asserted 0.01 rather than touching the new default.

Entry point

Use python src/share/scripts/record.py, not the installed share-record

The share-record console script doesn't list rail_bimanual_grasp among --env.type's valid choices — it isn't picking up experiments's env registrations, likely a stale or narrower install than the checked-out source. Every command in this doc now runs the script by path instead, which is confirmed working and is already how steps B–D invoke everything.

Commands match the pattern established earlier this session for record.py, cross-checked against make_policies_and_datasets() in share/utils/control_utils.py for the dataset-per-primitive convention.
